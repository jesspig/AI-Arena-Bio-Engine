# 系统架构设计

## 1. 分层架构详解

系统按照分层架构设计，从界面层到底层引擎层依次划分为四个层次，每层职责明确，依赖关系单向向下。

### 1.1 层次划分与职责定义

| 层次 | 名称 | 核心职责 | 技术栈 | 依赖方向 |
| --- | --- | --- | --- | --- |
| 第一层 | 界面层 UI Layer | 用户输入、参数传递、列表展示 | React + Tailwind CSS | 依赖状态管理层 |
| 第二层 | 状态管理层 State Layer | 全局不可变状态管理、Action 派发 | React Context + useReducer | 无外部依赖 |
| 第三层 | 适配层 Adaptor Layer | React 与 p5 之间的桥梁、状态转换 | React Custom Hook | 依赖状态管理层和引擎层 |
| 第四层 | 引擎层 Engine Layer | 核心算法执行：脊柱约束、IK 求解、目标生成 | TypeScript 纯类 | 无任何依赖 |

### 1.2 层间交互规则

```mermaid

    subgraph "界面层"
        UI[UI Components]
    end
    
    subgraph "状态管理层"
        CTX[Context Provider]
        RDC[Reducer]

    CTX -->|调用| RDC
    RDC -->|返回新状态| CTX
    CTX -->|提供状态| UI
    CTX -->|提供状态| HOOK
    HOOK -->|调用| ENG
    CB -->|触发| HOOK
    CB -->|dispatch| CTX
    ENG -->|无回调| HOOK
```text
```mermaid

**交互规则说明**：

- **向下依赖**：每层只依赖下一层，不跨层调用
- **状态流**：界面层通过 dispatch 触发状态变更，状态管理层通过 Context 提供新状态
- **数据桥**：适配层从状态管理层读取数据，转换为引擎层可识别的格式
- **引擎独立性**：引擎层不依赖任何外部状态，所有数据通过参数传入

## 2. 模块职责矩阵

### 2.1 界面层组件职责

| 模块           | 职责                   | 输入                   | 输出             | 技术栈               |
| --- | --- | --- | --- | --- |
| Layout 组件    | 整体三列布局容器       | 子组件                 | 布局结构         | React + Tailwind CSS |
| CanvasPanel 组件 | 容纳 P5Canvas 组件，传递状态 | creatures、selectedId、dispatch | 动画渲染 | React + @p5-wrapper/react v5 |
| Sidebar 组件   | 左侧配置面板           | 当前选中生物配置、dispatch | 参数更新事件 | React DOM          |
| CreatureList 组件 | 右侧生物列表         | creatures 数组、selectedId、dispatch | 选中/删除事件 | React DOM        |

### 2.2 状态管理层模块职责

| 模块               | 职责                       | 输入           | 输出             | 技术栈           |
| --- | --- | --- | --- | --- |
| CreatureContext.tsx | Context Provider 与 Hook 导出 | 初始状态   | 状态对象 + dispatch | React Context |
| reducer.ts         | 纯函数状态转换             | 当前状态 + Action | 新状态       | TypeScript 纯函数 |

### 2.3 适配层模块职责

| 模块                | 职责                           | 输入                           | 输出               | 技术栈           |
| --- | --- | --- | --- | --- |
| useCreatureSketch Hook | 封装 sketch 函数与交互回调 | creatures、selectedId、dispatch | sketch 函数 + updater | React Custom Hook |

### 2.4 引擎层模块职责

| 模块        | 职责                               | 输入                   | 输出             | 技术栈       |
| --- | --- | --- | --- | --- |
| Creature.ts | 生物数据聚合与行为编排             | 配置对象、目标点       | 更新后的状态     | TypeScript 类 |
| Spine.ts    | 脊柱链式约束求解                   | 目标点、速度、节点数组 | 更新后的节点位置 | TypeScript 类 |
| Leg.ts      | 反向运动学求解与贴地逻辑           | 附着点、脚部位置、骨骼长度 | 关节坐标     | TypeScript 类 |

## 4. 数据流架构

### 4.1 从 React 到 p5 的数据流

```mermaid
flowchart LR
    A[React 状态变化] --> B[Context 更新]
    B --> C[Props 传递到 CanvasPanel]
    C --> D[sketch prop 更新]
    D --> E[P5Canvas 组件接收新 props]
    E --> F[updater 机制同步到 p5]
    F --> G[p5 draw 循环读取新状态]
    G --> H[Creature.update 使用新配置]
```mermaid

**数据流说明**：

1. React 状态通过 Context 传递给 CanvasPanel
2. CanvasPanel 将状态作为 props 传入 sketch 函数
3. @p5-wrapper/react v5 的 updater 机制确保状态同步
4. p5 draw 循环每帧读取最新状态并更新生物

### 4.2 从 p5 到 React 的数据流

```mermaid
flowchart LR
    A[用户右键点击画布] --> B[p5 mousePressed 事件触发]
    B --> C[提取坐标和 selectedId]
    C --> D{selectedId 存在?}
    D -->|是| E[dispatch SET_TARGET Action]
    D -->|否| F[忽略点击]
    E --> G[Reducer 处理 Action]
    G --> H[更新对应生物的 target]
    H --> I[Context 广播新状态]
    I --> J[p5 通过 updater 获取新 target]
```mermaid

**数据流说明**：

1. 用户在 p5 画布中执行右键点击
2. mousePressed 回调检测 selectedId 非空
3. 通过 dispatch 派发 SET_TARGET Action
4. Reducer 更新对应生物的目标点
5. 新状态通过 Context 广播，p5 自动获取

## 7. 架构设计原则

### 7.1 单一职责原则

每个模块只负责一个明确的业务领域：

- Layout 组件只负责布局
- Sidebar 组件只负责配置面板
- reducer 只负责状态转换
- Creature 类只负责行为编排

### 7.2 开放封闭原则

- 引擎层通过参数化设计支持扩展
- 新增行为模式无需修改核心算法
- 适配层可替换，支持其他前端框架

### 7.3 接口隔离原则

- 函数签名只声明真正需要的参数
- Creature 不需要知道 React 的存在
- p5 只需要 sketch 函数，不需要了解状态管理

### 7.4 依赖倒置原则

- 核心业务逻辑不依赖外部服务
- 外部依赖通过函数参数传入
- 引擎层完全独立，可移植到其他框架

## 8. 架构优势分析

| 优势         | 说明                                               |
| --- | --- |
| **可测试性** | 引擎层无框架依赖，可独立进行单元测试               |
| **可移植性** | 引擎层可轻松移植到 Vue 3、Svelte 等其他框架       |
| **可维护性** | 分层架构清晰，修改影响范围可控                     |
| **可扩展性** | 参数化设计支持灵活配置，无需修改核心代码           |
| **性能优化** | 状态管理层使用 useReducer 提供时间旅行能力，便于调试 |

## 9. 架构约束与限制

### 9.1 技术约束

- p5.js 必须在浏览器环境中运行，不支持服务端渲染
- @p5-wrapper/react v5 要求 React 19+
- TypeScript 严格模式必须开启

### 9.2 性能约束

- 生物数量超过 20 个时需采用对象池模式
- 距离约束迭代次数建议控制在 3~4 次
- draw 循环中应避免频繁对象分配

### 9.3 兼容性约束

- 不支持 IE 浏览器
- 移动端性能需额外优化
- 多画布同时运行时需注意内存占用
